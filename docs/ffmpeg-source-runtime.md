# AVID Core runtime acquisition

AVID Core owns the FFmpeg/FFprobe source, recipe, native builds and runtime contract. ATIV never builds or selects a separate distribution. Production still uses the exact six-target build identity in `runtime/core-runtime.json`, with original archive, source, executable and manifest hashes.

The shared `script/core_runtime.py` verifies the expected repository, release tag, promotion workflow, release revision, manifest digest and matched runtime identity before extraction or execution. Normal builds acquire the published `ffmpeg-9.0.1-r7.1` release, whose manifest SHA-256 is `ef7eb4e2b62f656aa3cb6808dc2d227eb035be2050367d596e1f79a6d6d45779`. The Rust library and native tool build are pinned to `25d19098a22936638b0e2a70616083d929fe409c`; the release promotion revision is `2e137df692aa612e0dd62ebd93b5fff26c61663a`. There is no system/PATH fallback or first-launch media-tool download.

For unpublished host qualification only, set `AVID_CORE_QUALIFICATION=1` locally or dispatch `native-release.yml` with `qualify_core_candidate=true`. Candidate origin is pinned to Core commit `25d19098a22936638b0e2a70616083d929fe409c`, maintainer dispatch run `36681249099`, six actual native jobs and GitHub artifact digests. PR/push publication cannot acquire candidates.

Final packages preserve Core metadata and corresponding source. `signed-payload.json` records original and signed derivative hashes without rewriting Core's original checksum manifest. Packaging validates the compiled Core identity and both bundled tools with an empty PATH. See [release integration](release-integration.md) for signing configuration and remaining gates.

## Independent platform releases: migration status

`runtime/platform-runtimes.json` separately pins six immutable AVID Core platform releases. Every entry identifies one target's version, recipe, tag, release and source revisions, successful native job, Actions artifact, and the SHA-256 and GitHub asset ID of each published file. The initial pins use FFmpeg 9.0.1 recipe 7 from build run `38182234949`; targets can later move independently. `script/platform_runtime.py` checks the selected release's immutable GitHub identity, target job and artifact provenance. It requires a GitHub attestation for that release's `platform-release.json`, bound to the provider publisher workflow, its exact source revision and `refs/heads/main`. Only then does it download the runtime and sources, verify every pinned asset and both checksum sidecars, reject unexpected release assets, validate archive contents and executable architecture, and install the selected target. An unrelated failed or unfinished target job does not affect this origin check. A failure removes the temporary acquisition directory and never falls back to PATH or an unsigned download.

**Provider gap:** AVID Core's current per-platform releases have `immutable: true`, SHA-256 checksums and `platform-release.json`, but no GitHub attestation for that provenance file. `gh attestation verify` returns HTTP 404. A checksum pinned in ATIV identifies bytes but does not authenticate who produced them. The new verifier therefore rejects these releases before fetching executable bytes. AVID Core must attest `platform-release.json` in its per-platform publisher with `attestations: write`, publish the attestation against the immutable release, and document the signing workflow/ref. The attested provenance already binds runtime and source hashes. ATIV's new pins then need updating to an attested release and its verified publisher revision.

The current application build, package, host evidence and embedded Rust runtime validator remain on the authenticated `ffmpeg-9.0.1-r7.1` path. That validator currently requires the runtime build revision to equal ATIV's pinned AVID Core library revision; independent builds use newer Core revisions. Before production can use a newly attested platform release, ATIV must verify API/spec compatibility, change the embedded per-target identity checks and package receipt to accept the selected runtime revision, then complete native media and package tests for that target. This work is local to ATIV and does not make other platforms wait. Until then, development publication continues with the existing authenticated runtime and signed automatic updates keep their separate verification.

To check a candidate release without changing production, run `python3 script/platform_runtime.py macos-arm64 --destination build/core-acquisition/platform-qualification/macos-arm64`. The current release fails closed at attestation; the destination is not created. `python3 -B script/test_platform_runtime.py` exercises the local origin, pin, corruption and failure checks.
