# Windows distribution licensing audit

Reviewed 2026-09-24 against the published `v0.2.4` x64 and ARM64 portable ZIPs. This is a component analysis, not a claim that Microsoft code is GPL licensed. The exact filename, SHA-256, origin evidence, and package license URL for every `.dll`, `.exe`, `.winmd`, `.pri`, `.xbf`, and `.dat` in both archives are in [windows-distribution-inventory.json](windows-distribution-inventory.json). The companion [inventory script](../script/windows_distribution_inventory.py) reproduces the comparison against the NuGet cache. Its limits matter: the x64 .NET 8.0.30 package was absent locally, so `.deps.json` identifies those assets; a filename match alone is not proof of origin. `ATIV.pri` is an application-generated resource index, not a Microsoft runtime binary.

The published archives have SHA-256 `e029333489c702e58198296930b21d8ad4f640e85596e4a640fc918a5bcc9e94` (x64) and `1085cb7f8798a08467674958b5f4ff01ed04015e909df2947ab083eaee909a6a` (ARM64). Current [installer input](../platform/windows/installer/ATIV.iss) copies the portable publish directory, so the same analysis applies to installer payloads; the installer executable itself was not separately downloaded or unpacked for this audit.

## Rules used

GPLv3 [section 1](https://www.gnu.org/licenses/gpl-3.0.en.html) defines System Libraries by their relationship to an operating system major component, compiler, or object-code interpreter and excludes qualifying libraries from Corresponding Source. The [GNU FAQ on System Libraries](https://www.gnu.org/licenses/gpl-faq.en.html#SystemLibraryException) confirms that linking a GPL program to a qualifying proprietary system library can be permitted. Its [Windows runtime answer](https://www.gnu.org/licenses/gpl-faq.en.html#WindowsRuntimeAndGPL) treats the Visual C++ runtime as a System Library when linked, but says its compiled DLLs cannot be distributed with the GPL program under that exception. For a non-System-Library GPL-incompatible library, the [GNU FAQ](https://www.gnu.org/licenses/gpl-faq.en.html#GPLIncompatibleLibs) describes a narrow GPLv3 section 7 additional permission from the copyright holders of the GPL code. Mere Microsoft authorship, proprietary terms, or physical proximity does not by itself decide whether separate files form one GPL-covered work.

[SignPath Foundation's conditions](https://signpath.org/terms.html) are a **separate** test: project components must use OSI-approved licenses and signed packages cannot contain proprietary code, **except that System Libraries may be included in signed packages**. A qualifying System Library therefore need not be removed merely to seek SignPath eligibility. SignPath also limits signing to the project's own binaries and imposes process and release requirements. Its ultimate eligibility decision belongs to SignPath.

## Boundary and smallest practical changes

1. **Owned source:** Keep `GPL-3.0-or-later` on all ATIV-authored code. Microsoft runtime terms do not transfer ownership or alter that source license. AVID Core's GPL-3.0-only dependency limits the combined Rust engine to GPLv3, independently of Microsoft.
2. **Current portable package:** It contains GPL ATIV binaries, MIT/BSD dependencies, and proprietary Windows App SDK binaries side by side. It is inaccurate to label every file or the entire ZIP `GPL-3.0-or-later`. The Windows App SDK [redistribution terms §3](https://www.nuget.org/packages/Microsoft.WindowsAppSDK.WinUI/2.3.6/License) explicitly permit binplaced files but impose recipient-protective terms and forbid putting Microsoft's distributable code under source/modification-right terms. Preserve the individual license boundaries and include required Microsoft notices/terms in future packages.
3. **Combined Windows application:** WinUI and some support components are linked or loaded by `ATIV.dll`. They have not been established as GPLv3 System Libraries, even though Windows OS and VC++ runtime components can qualify. GNU's guidance points to a narrow GPLv3 §7 additional permission for the ATIV-owned Windows UI files if a non-System-Library proprietary link is unavoidable. Only ATIV copyright holders can grant it; it must not purport to relicense Microsoft's files or AVID Core. A Windows-specific additional permission is smaller than changing the license of all ATIV code. Verify the Windows SDK projection's exact terms at the same time.
4. **SignPath package:** SignPath explicitly allows System Libraries in signed packages, so a blanket ban on Microsoft redistributables is wrong. For the Windows App SDK files and Windows SDK projection in this particular ZIP, System Library qualification is not established. A framework-dependent WinUI build that installs Microsoft's runtime outside the signed package is the cleanest candidate, while retaining separately licensed MIT/BSD files. This needs a Windows build/run test and SignPath review; it is not a reason to abandon GPL-3.0-or-later for owned code.
5. **Remove avoidable binaries first:** Test replacing the broad `Microsoft.WindowsAppSDK` reference with `Microsoft.WindowsAppSDK.WinUI/2.3.6`. Its [declared dependencies](https://www.nuget.org/packages/Microsoft.WindowsAppSDK.WinUI/2.3.6) omit AI, Windows ML, Search and Widgets. This specifically removes the unneeded Windows ML package with Intel MKL notices if the rebuilt output confirms the dependency disappears. Then inventory and test both architectures, inspect any bootstrapper and SDK projection, and decide whether a self-contained ZIP remains a separate convenience distribution while a framework-dependent package is submitted to SignPath. Recheck exact archives after each build; this audit does not certify a future artifact.
